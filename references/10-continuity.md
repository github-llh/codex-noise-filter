# 长任务、压缩与恢复

## 何时建立检查点

仅在以下情况维护短检查点：

- 多文件或多阶段任务，当前状态无法从单个 diff 恢复。
- 即将运行长时间、高输出或可能中断的工具。
- 上下文即将压缩、切换窗口/模型，或需要交接给后续任务。
- 同一问题已失败，需要防止重复路径。

不要按固定读取文件数、工具调用次数或每次写入强制输出检查点。

## 检查点内容

```text
目标:
当前事实:
已改文件:
验证状态:
doNotRetry:
下一步:
```

只记录恢复所需事实和证据锚点，不保存大段日志、外部 prompt、秘密、机器专属路径或过时猜测。

## 恢复顺序

1. 重新读取最新用户目标和高优先级指令。
2. 查看 `git status`、`git diff`、当前文件和仍在运行的工具状态。
3. 将旧检查点当作线索，用当前文件与命令结果复核。
4. 确认哪些操作已落盘、哪些未执行、哪些验证已过期。
5. 从唯一下一步继续，不从零重扫，也不盲信最后一次工具输出。

## 防复发

- 同一命令或假设连续失败两次后写入 `doNotRetry`，并说明替代证据路径。
- 用户指出“之前已改过/不要再试”时，先找当前代码、diff 或历史记录验证旧结论。
- 工作区事实与旧检查点、memory 或第三方摘要冲突时，以当前工作区和最新规则为准。

## Memory 边界

- 读取 memory 只用于稳定偏好、历史决策和恢复线索；易漂移事实要现场验证。
- 未经用户明确要求不写长期 memory。
- 不把凭证、客户数据、临时日志、外部 prompt 或未验证结论写入 memory。

## 交付

最终回复不需要展示完整检查点。只报告用户继续工作需要的当前结果、验证缺口和下一步。
